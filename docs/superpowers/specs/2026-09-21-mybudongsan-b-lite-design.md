# MyBudongsan B-Lite 설계

- 상태: 승인된 설계
- 작성일: 2026-09-21
- 대상: 개인용 아파트 매수 조사 에이전트 V1
- 구현 방식: Codex 에이전트 + Python CLI + SQLite

## 1. 목적

MyBudongsan은 사용자의 매수 조건을 구조화하고, 실제 활성 매물과 공식 자료를 조사한 뒤, 근거가 연결된 후보 비교 보고서를 만드는 개인용 조사 도구다.

V1의 목표는 부동산 의사결정을 자동으로 대신하는 것이 아니다. 반복적인 매물 발굴, 자료 정리, 비교, 출처 확인을 줄이고 사용자가 현장 확인과 최종 판단에 집중하게 하는 것이 목표다.

## 2. 핵심 설계 원칙

1. 필수조건을 먼저 적용하고 점수는 그다음에 계산한다.
2. 검색결과와 실제 활성 매물 확인을 구분한다.
3. 공식자료와 개별 매물 페이지를 우선하고 블로그·언론은 참고 단서로만 사용한다.
4. 매물의 적합도와 조사 근거의 신뢰도를 별도로 평가한다.
5. SQLite를 유일한 정본으로 사용한다.
6. 일반 조사에는 최소한의 에이전트만 사용하고 전문가를 조건부로 호출한다.
7. 중단된 조사는 마지막 체크포인트부터 재개한다.
8. 사용자의 승인 없이 필수조건을 자동으로 완화하지 않는다.
9. 미래 확장을 위한 서버·큐·범용 추상화를 미리 만들지 않는다.

## 3. V1 범위

### 3.1 포함

- PM 에이전트와 통합 부동산 조사원
- 필요한 경우에만 추가하는 전문 에이전트 한 명
- 대화 또는 Google Sheets 기반 매수 요청서 작성
- 최대 5개 지역 입력
- 정확 지역 검색과 선택적인 주변 확장
- ego-browser를 이용한 매물 및 웹자료 조사
- 후보 15~25개 발견, 실제 매물 7개 검증, 최종 최대 3개 심층분석
- 필수·선호·제외 조건 관리
- SQLite 정본 데이터 저장
- Markdown 보고서, CSV, JSON 생성
- Google Sheets 기본 결과 동기화
- Google Drive 회차별 보고서 저장
- 체크포인트와 중단 지점 재개
- WATCH 매물 수동 갱신
- 작업 단계별 제한 알림: PlayMCP 카카오 나챗방, 완료·실패 시 Gmail 병행

### 3.2 제외 및 비약속 항목

다음 항목은 예정 기능이 아니다. 실제 필요가 확인될 때만 새롭게 검토한다.

- 매 조사마다 전문가 3명 병렬 실행
- 모든 후보에 대한 독립 검증 에이전트
- 후보 30~50개 고정 수집
- 실시간 Google Sheets 대시보드
- 자동 일일 관심 매물 감시와 매물 변화 알림
- FastAPI 또는 Flask 서버
- 작업 큐, 웹 UI, 다중 사용자 기능
- 자동 중개사 연락
- 벡터 데이터베이스와 범용 워크플로 엔진

## 4. 시스템 구조

### 4.1 Codex 판단 계층

#### PM 에이전트

- 사용자와 직접 소통한다.
- 자연어 요구를 매수 요청서로 변환한다.
- 요청서의 누락과 충돌을 확인하고 승인받는다.
- 통합 조사원에게 조사 범위를 전달한다.
- 필요한 경우 전문 에이전트 한 명을 추가한다.
- 근거와 평가를 종합해 최종 보고서를 작성한다.
- 작업 단계가 바뀌면 정해진 알림 이벤트를 발생시킨다.

#### 통합 부동산 조사원

- 후보 매물을 발견한다.
- 실제 개별 매물 페이지를 확인한다.
- 실거래가, 기본 단지정보, 교통과 생활권을 함께 조사한다.
- 자료를 구조화된 결과와 증거 목록으로 반환한다.

#### 조건부 전문 에이전트

아래 역할 중 조사 병목에 가장 적합한 한 명만 추가한다.

- 도시계획·정책: 정비사업, 교통계획, 개발계획, 규제 조사
- 가격·시장: 호가와 실거래 차이, 거래량, 환금성, 가격방어 분석
- 교통·생활권: 여러 출퇴근 목적지, 환승, 생활권 비교

호출 조건은 다음과 같다.

- 개발계획이 매물 판단에 큰 영향을 주는 경우
- 호가와 실거래 차이가 커 가격판단이 어려운 경우
- 여러 출퇴근 목적지 비교가 복잡한 경우
- 핵심 출처 간 정보가 충돌하는 경우

### 4.2 Python 실행·데이터 계층

Python은 판단이 아니라 반복 가능성과 데이터 정합성을 담당한다.

- Typer: CLI 진입점
- Pydantic: 매수 요청서와 조사 결과 검증
- SQLAlchemy와 SQLite: 정본 데이터 관리
- Alembic: 스키마 변경 관리
- Google API 클라이언트: Sheets, Drive, 완료·실패 Gmail 연동
- PlayMCP `MemoChat`: 카카오톡 나챗방 진행 알림
- Jinja2와 Markdown: 보고서 생성
- pytest: 단위 및 통합 테스트

V1에는 HTTP 서버가 없다. 사용자는 Codex의 PM과 대화하고 PM이 Python CLI를 호출한다.

## 5. 매수 요청서

### 5.1 저장형 구매자 프로필

- 가용 예산 범위
- 대출 사용 가능 범위
- 취득세·수리비 포함 여부
- 주요 출퇴근 목적지
- 허용 통근시간
- 입주 희망 시점
- 예상 보유기간
- 실거주와 투자 목적 비중
- 기본 평가 가중치

민감한 재무정보는 정확한 값 대신 범위로 저장한다.

### 5.2 회차별 검색 요청

- 요청 ID, 이름, 버전
- 조사 지역 최대 5개
- 정확 검색 또는 주변 확장 허용 여부
- 매매가격 범위
- 전용면적과 방 개수
- 준공연도 또는 허용 연식
- 세대수, 주차, 층, 방향 등
- 입주 가능 시점
- 필수 조건
- 선호 조건
- 제외 조건
- 특별 조사 항목
- 후보 수와 조사 깊이

승인된 요청서 버전은 수정하지 않는다. 조건을 바꾸면 새 버전을 생성한다.

### 5.3 요청 상태

```text
DRAFT -> NEEDS_CONFIRMATION -> APPROVED -> RUNNING -> COMPLETED
                                      \-> RESUMABLE
                                      \-> CANCELLED
```

V1에서 Google Sheets 요청은 자동으로 조사를 시작하지 않는다. 사용자가 PM에게 실행을 요청하면 PM이 `APPROVED` 상태의 요청서를 가져와 최종 확인 후 실행한다.

## 6. 조사 파이프라인

1. 대화 또는 Sheets에서 요청을 접수한다.
2. PM이 요청서를 구조화하고 누락·충돌을 확인한다.
3. 사용자가 최종 요청서 버전을 승인한다.
4. 요청서와 실행 레코드를 SQLite에 저장한다.
5. 통합 조사원이 후보 15~25개를 발견한다.
6. Python이 중복, 예산, 필수조건, 필수필드를 자동검사한다.
7. 후보 7개의 개별 매물 페이지를 확인한다.
8. 필요할 때만 전문 에이전트 한 명을 호출한다.
9. 최종 후보 최대 3개를 심층조사한다.
10. Python 검증과 PM의 근거 검토를 수행한다.
11. PM이 시나리오별 추천 보고서를 작성한다.
12. SQLite 저장 후 Sheets와 Drive에 동기화한다.

적합한 후보가 부족하면 자동 완화하지 않는다. PM은 예산, 지역, 연식, 면적 중 완화 가능한 시나리오를 제시하고 사용자 승인을 기다린다. 승인된 완화안은 새 요청서 버전으로 실행한다.

## 7. 데이터 설계

### 7.1 저장소 책임

| 저장소 | 책임 |
|---|---|
| SQLite | 요청서, 매물, 상태, 평가, 증거의 정본 |
| Google Sheets | 요청 입력, 상태와 최종 결과 열람 |
| Google Drive | 보고서와 CSV/JSON 회차 백업 |
| 로컬 파일 | 체크포인트, 제한된 스크린샷, 임시자료 |

Sheets에서 결과 영역을 수정해도 SQLite로 역반영하지 않는다. 사용자가 수정할 수 있는 영역은 검색 요청과 WATCH 표시다.

### 7.2 최소 테이블

- `buyer_profiles`: 저장형 구매자 프로필
- `search_requests`: 요청서, 버전, 유연한 조건 JSON
- `research_runs`: 실행 상태, 단계, 시각, 오류, 체크포인트
- `listings`: 출처와 원본 매물 ID를 기준으로 한 매물 식별자
- `listing_snapshots`: 시점별 가격, 상태, 매물 설명
- `evidence`: 주장, 출처, 확인 시각, 자료 유형, 핵심 근거
- `assessments`: 조건 충족, 점수, 위험, 판단 사유
- `reports`: 생성 산출물과 Drive 위치

### 7.3 중복 판정

1. 출처 사이트의 매물 ID
2. 단지·동·층·면적·가격·중개업소 조합
3. 명확하지 않으면 자동 병합하지 않고 `duplicate_suspected`로 표시

같은 매물의 새 관측은 `listing_snapshots`에 추가한다.

## 8. 증거 정책

### 8.1 자료 우선순위

1. 정부·지자체·공공기관 공식자료
2. 실거래 및 공공데이터
3. 개별 활성 매물 페이지
4. 신뢰 가능한 보조자료
5. 언론·블로그는 참고 단서

### 8.2 보존 수준

- 후보 15~25개: URL과 최소 메타데이터
- 검증 7개: 가격, 상태, 핵심 조건, 출처, 확인 시각
- 최종 최대 3개: 핵심 문장과 필요한 스크린샷
- 개발계획: 기관, 문서명, 발표일, URL, 진행 단계

개발계획은 `확정`, `추진`, `검토`로 구분한다. 전체 웹페이지 복제는 하지 않는다.

PM에게는 원문 전체가 아니라 구조화된 결과와 필요한 핵심 근거만 전달해 토큰 사용량을 제한한다.

## 9. 평가 모델

### 9.1 필수 게이트

1. 필수조건 통과
2. 제외조건 부재
3. 활성 매물 여부 확인
4. 최소 증거 충족

필수 게이트를 통과하지 못한 매물은 추천 점수와 무관하게 탈락한다.

### 9.2 기본 가중치

| 평가 영역 | 비중 |
|---|---:|
| 환금성·가격방어 | 35 |
| 교통·출퇴근 | 30 |
| 가격 적정성·실거래 비교 | 25 |
| 주거 품질·개별 위험 | 10 |

점수마다 판단 사유와 출처를 연결한다. 근거가 없으면 높은 점수를 부여하지 않는다.

### 9.3 적합도와 조사 신뢰도

- 매물 적합도: 사용자 조건과의 적합성
- 조사 신뢰도: 판단 근거의 충분성과 최신성

조사 신뢰도가 85점 미만이면 매수 추천으로 확정하지 않는다. 부족한 증거와 확인 방법을 보고한다.

## 10. 보고서

최종 후보를 무조건 1~3위로 채우지 않는다. 후보가 충분할 때 다음 시나리오로 표현한다.

- 종합 추천
- 안정성 대안
- 조건 특화 대안

유효 후보가 하나뿐이면 하나만 추천할 수 있고, 모든 후보가 부족하면 `추천 없음` 결론을 허용한다.

보고서 목차는 다음과 같다.

1. 요청 조건 요약
2. PM 결론
3. 최종 후보 비교표
4. 후보별 추천·보류·제외 사유
5. 가격과 실거래 분석
6. 교통 및 생활권
7. 도시계획·정책 영향
8. 위험과 미확인 사항
9. 현장 방문 및 중개사 문의 체크리스트
10. 출처와 조사 기준시각

## 11. Google 연동

### 11.1 Sheets 최소 탭

- `검색 요청`: 사용자 입력
- `조사 현황`: 요청과 실행 상태
- `추천 결과`: 최종 후보 요약
- `관심 매물`: WATCH 목록과 마지막 수동 확인 결과

### 11.2 Drive 구조

```text
MyBudongsan/
└── YYYY/
    └── MM/
        └── 요청ID_요청이름/
            ├── report.md
            ├── candidates.csv
            ├── run-data.json
            └── evidence/
```

`run-data.json`은 해당 회차의 읽기 전용 백업이다.

### 11.3 인증

- 개인 Google 계정 OAuth 2.0을 사용한다.
- OAuth 토큰은 macOS Keychain 또는 로컬 보안 저장소에만 보관한다.
- 저장소, SQLite, Sheets, 로그에 토큰·쿠키·로그인정보를 남기지 않는다.

## 12. 오류와 복구

- 각 파이프라인 단계 완료 시 체크포인트를 저장한다.
- 같은 요청 버전과 단계에 멱등키를 사용한다.
- 일시적인 페이지 오류는 최대 3회 재시도한다.
- 로그인, CAPTCHA, 권한 문제는 즉시 사용자에게 요청한다.
- 사이트 차단을 우회하지 않고 대체 공식자료를 찾는다.
- Google 동기화가 실패해도 로컬 결과를 보존하고 동기화만 재시도한다.
- 2시간 내 완료하지 못하면 현재 결과와 부족한 항목을 보고한다.
- 재실행 시 성공한 단계를 반복하지 않는다.

## 13. 작업 진행 알림

알림은 새 조사를 수행하지 않는다. 이미 저장된 실행 상태와 짧은 요약만 전달한다.

### 13.1 알림 순서

한 조사 작업의 알림은 최대 5회를 원칙으로 한다.

1. `WORK_STARTED`: 작업 시작과 승인된 조건 요약을 카카오 나챗방으로 전송
2. `RESEARCHER_ASSIGNED`: 통합 부동산 조사원에게 전달되었음을 카카오 나챗방으로 전송
3. `SPECIALIST_ASSIGNED`: 조건부 전문 에이전트를 호출했을 때만 카카오 나챗방으로 전송
4. `FINALIZING`: 후보 검증을 마치고 보고서를 작성할 때 카카오 나챗방으로 전송
5. `COMPLETED`: 작업 결론과 보고서 위치를 카카오 나챗방과 Gmail로 전송

전문 에이전트를 호출하지 않으면 3번 알림은 생략한다. 상태 변화가 없으면 알림을 보내지 않는다.

### 13.2 사용자 조치 및 실패

- 로그인, CAPTCHA, 권한 오류 등은 `NEEDS_ACTION`으로 즉시 알린다.
- `NEEDS_ACTION`은 다음 일반 진행 알림을 대체한다.
- 조치 후 재개되면 중간 알림을 줄이고 마지막 `COMPLETED` 또는 `FAILED` 슬롯을 남긴다.
- `FAILED`는 카카오 나챗방과 Gmail로 전송한다.
- 알림 실패가 조사 자체를 실패시키지는 않는다. 실패를 실행 기록에 남기고 해당 채널만 재시도한다.

### 13.3 중복 방지와 채널

- 진행 알림: PlayMCP 카카오톡 나챗방
- 완료·실패 알림: 카카오톡 나챗방과 Gmail
- 실행 ID와 이벤트 유형의 조합을 멱등키로 사용한다.
- 체크포인트에서 재개하더라도 이미 성공한 알림은 다시 보내지 않는다.
- PlayMCP 토큰과 Google OAuth 토큰은 저장소, SQLite, Sheets, 로그에 기록하지 않는다.

## 14. WATCH 동작

V1의 WATCH는 수동 기능이다.

1. 사용자가 Sheets 또는 PM 대화에서 매물을 WATCH로 표시한다.
2. 사용자가 갱신을 요청한다.
3. Python이 새 스냅샷과 이전 스냅샷을 비교한다.
4. 가격, 상태, 매물 삭제·재등록 의심을 결과에 표시한다.

WATCH 자동 스케줄과 매물 변화 메시지 알림은 포함하지 않는다.

## 15. 개인정보와 책임 범위

- 재무정보는 가능한 한 범위로 저장한다.
- 로그에는 인증정보와 브라우저 세션 정보를 남기지 않는다.
- 보고서에는 자료 기준시각과 미확인 사항을 명시한다.
- 보고서는 조사 지원 자료이며 법률·세무·대출·감정평가 또는 매수 보증이 아니다.
- 중요한 사실은 현장 방문, 중개사, 등기·공부, 금융기관 등을 통해 사용자가 최종 확인한다.

## 16. V1 완료 기준

- 대화로 매수 요청서를 생성하고 승인할 수 있다.
- 최대 5개 지역을 입력하고 요청서 버전을 보존한다.
- ego-browser로 후보를 발견하고 개별 활성 매물을 확인한다.
- 중복 매물을 하나의 매물과 여러 스냅샷으로 관리한다.
- 7개 검증 후 최대 3개 심층보고서를 생성한다.
- 출처와 조사 시각을 보고서에 표시한다.
- 조사 신뢰도 85 미만의 결과를 추천으로 확정하지 않는다.
- 중간 중단 후 체크포인트에서 재개한다.
- SQLite 결과를 기본 Sheets와 Drive에 반영한다.
- WATCH 매물을 수동 갱신해 가격·상태 변화를 확인한다.
- 매물이 없을 때 자동 완화하지 않고 사용자 승인 요청을 만든다.
- 한 작업의 진행 알림을 최대 5회로 제한하고 완료·실패를 지정 채널로 전달한다.

## 17. 테스트 전략

### 단위 테스트

- 요청서 검증과 최대 지역 수
- 필수·선호·제외 조건 판정
- 평가 가중치 계산
- 중복키와 멱등키 생성
- 실행 상태 전이
- 체크포인트 재개
- 스냅샷 변화 비교
- 보고서 템플릿 렌더링
- 알림 횟수 제한, 조건부 생략, 멱등키 판정

### 통합 테스트

- SQLite 마이그레이션과 회차 저장
- Google OAuth와 테스트용 Sheets·Drive·Gmail 동기화
- 구조화된 브라우저 조사 결과 가져오기
- 중단 후 재개와 중복 방지
- PlayMCP 테스트 나챗방과 Gmail 테스트 수신처로 알림 전달

### 수동 실제 웹 검증

- 검색결과와 개별 활성 매물의 구분
- 로그인·CAPTCHA 발생 시 정지 동작
- 공식자료 출처와 진행 단계 분류
- 최종 보고서의 링크와 기준시각 확인

## 18. 예상 실행 비용 통제

- 일반 실행은 PM과 통합 조사원만 사용한다.
- 전문 에이전트는 한 명만 조건부 호출한다.
- 원문 전체를 에이전트 사이에서 반복 전달하지 않는다.
- 자동검사는 Python으로 처리한다.
- 최종 최대 3개에만 깊은 검증을 집중한다.
- 자동 스케줄과 변화 없는 WATCH 분석을 실행하지 않는다.
- 알림은 저장된 상태를 재사용하며 알림 생성을 위해 별도 에이전트를 호출하지 않는다.

이 기준은 최초의 전체 B안보다 조사 회차당 모델 사용량과 시간을 크게 줄이면서, 데이터 정합성과 재현 가능성은 유지하기 위한 것이다.
